# 开发与扩展指南

> 面向要把这套 CMS 跑起来、改下去的人。架构层面为什么这么设计，看 [`02-CMS架构设计方案.md`](./02-CMS架构设计方案.md)；这里只讲怎么动手。
> 给 AI 编码代理的版本更精简（命令 + 铁律 + 坑位）：[`AGENTS.md`](../AGENTS.md)。

## 1. 环境要求

| 项 | 要求 | 说明 |
| --- | --- | --- |
| Node.js | ≥ 22（实测 24.21） | 需要全局 `fetch`、`Intl.Segmenter`、Web Crypto |
| pnpm | 10.x | workspace 依赖两个包 |
| Cloudflare 账号 | 仅在部署时需要 | 本地开发不需要 |

不需要 Docker、不需要本地数据库：D1 / KV / R2 都由 wrangler 在本地模拟，状态存在 `.wrangler/state`。

## 2. 第一次跑起来

```bash
pnpm install                    # 1. 装依赖
pnpm db:migrate                 # 2. 建本地 D1 表结构（含 FTS5 虚表）
pnpm build:console              # 3. 构建后台 SPA（Worker 用它作为静态资源）
pnpm dev                        # 4. 启动 Worker(8787) 与后台开发服务器(5173)
```

初始化站点所有者（只需一次，用户表为空时才允许）：

```bash
curl -X POST http://127.0.0.1:8787/api/auth/setup \
  -H 'Content-Type: application/json' \
  -d '{"email":"owner@example.com","username":"owner","displayName":"站长","password":"Taiping@2026"}'
```

或者灌一份完整的演示数据（它走的是公开 API，顺带验证整条链路）：

```bash
node scripts/seed.mjs
```

脚本会创建 6 篇文章、2 个页面、3 条动态、2 个项目、10 个分类标签、7 条导航、5 个自定义字段，并提交几条待审核评论。账号是 `owner@taiping.local` / `Taiping@2026`。

### 端口与入口

| 地址 | 内容 | 备注 |
| --- | --- | --- |
| <http://127.0.0.1:8787/> | 前台 | 服务端渲染，改主题文件后热重载 |
| <http://127.0.0.1:8787/admin> | 后台 | 用 `build:console` 的产物 |
| <http://localhost:5173/> | 后台（开发） | 有 HMR，`/api` 已代理到 8787 |
| <http://127.0.0.1:8787/api/doc> | OpenAPI JSON | 与代码同步生成 |
| <http://127.0.0.1:8787/api/reference> | Swagger UI | 可直接试接口 |

**日常开发建议只用 5173 改后台、用 8787 看前台。** 后台改完要发布进 Worker 时才跑 `build:console`。

## 3. 日常命令

| 命令 | 作用 | 什么时候用 |
| --- | --- | --- |
| `pnpm dev` | 并行启动两者 | 日常 |
| `pnpm dev:worker` | 只启 Worker | 只调接口或前台时 |
| `pnpm dev:console` | 只启后台 | 只改后台时 |
| `pnpm typecheck` | 服务端 + 后台 tsc | 提交前 |
| `pnpm test:unit` | 纯函数测试（秒级） | 改 `lib/` 时随手跑 |
| `pnpm test:workers` | workerd 集成测试（约 6 秒） | 改接口、权限、缓存时 |
| `pnpm test` | 两者都跑 | 提交前 |
| `pnpm db:generate` | 由 schema 生成迁移 | 改了 `db/schema.ts` |
| `pnpm db:generate --custom --name=<名字>` | 生成空迁移占位 | 要写 drizzle 表达不了的 DDL |
| `pnpm db:migrate` | 应用到本地 | 每次新增迁移后 |
| `pnpm build` | 构建 SPA + dry-run 打包 Worker | 部署前自检 |

## 4. 数据库操作

### 4.1 改表结构

```bash
# 1. 改 apps/server/src/db/schema.ts
pnpm db:generate              # 2. 生成 000N_xxx.sql（自动分配序号，更新 journal）
pnpm db:migrate               # 3. 应用到本地 .wrangler/state
pnpm typecheck                # 4. 类型会跟着变
```

三条纪律：

1. **不要手写 SQL 丢进 `apps/server/migrations/`**。原因见 [`adr/0007`](./adr/0007-手写DDL走自定义迁移.md)。
2. **改了迁移必须重跑 `db:migrate`**。本地状态是持久的，只改文件不重跑，表现是「代码改了但查询报 no such column」。
3. **不要修改已经执行过的迁移文件**。wrangler 按文件名记录已执行，改内容不会重跑，要改就新增一条。

### 4.2 直接查本地库

```bash
npx wrangler d1 execute DB --local --persist-to .wrangler/state \
  --command "select id, title, status, published_at from contents limit 10"
```

加 `--json` 便于管道处理。

### 4.3 从头再来

```bash
rm -r .wrangler/state          # PowerShell: Remove-Item -Recurse -Force .wrangler/state
pnpm db:migrate
node scripts/seed.mjs
```

### 4.4 全文索引

FTS 表由写入路径维护（发布或更新已发布内容时刷新），不需要手工干预。如果怀疑索引不一致：

```bash
curl -X POST http://127.0.0.1:8787/api/settings/maintenance/run -b <cookie>
```

它会重新跑一遍定时任务（含 `tasks` 表里排队重建索引的条目）。

## 5. 测试

### 5.1 两套配置，不要混

| 配置 | 环境 | 覆盖 | 适用 |
| --- | --- | --- | --- |
| `vitest.config.ts` | Node | `apps/server/src/**/*.test.ts` | 纯函数：slug、Markdown、权限判定、口令、分页、分词 |
| `vitest.workers.config.ts` | workerd | `tests/**/*.integration.test.ts` | 需要 D1 / KV / R2 / 完整中间件链的场景 |

集成测试通过 `cloudflare:test` 的 `SELF.fetch` 打真实入口，走完 `app.ts` 的全部中间件，不是直接调 handler —— 这样中间件顺序错了也能测出来。

### 5.2 写集成测试的三个必做动作

```ts
import { beforeEach } from "vitest";
import { createClient, resetState, setupOwner } from "./helpers";

let client: Client;

beforeEach(async () => {
  await resetState();              // 1. 清表 + 清 KV + 关页面缓存
  client = createClient();         // 2. 每个测试一个新客户端（自带 cookie 罐）
  await setupOwner(client);        // 3. 初始化 owner 拿到登录态
});
```

`resetState()` 为什么必须调：Workers 测试池的隔离存储**按文件**生效，同一文件内多个 `it` 之间数据会累积，第二次 `setup` 会拿到 409。它同时把 `site.pageCacheEnabled` 设为 false，避免「改了设置但页面没变」的假失败。

### 5.3 已知的测试易错点

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 第二个用例 setup 返回 409 | 没调 `resetState()` | 见上 |
| 改了设置但页面没变 | 页面缓存生效 | `resetState()` 会关掉 |
| 断言 422 而不是 403 | zod 校验在权限断言之前 | 测权限时请求体必须是合法数据 |
| 解锁保护内容后仍看不到正文 | 只发了会话 cookie，没发解锁 cookie | `createClient()` 的 cookie 罐会自动带上 |

## 6. 扩展

### 6.1 新增插件

1. 新建 `apps/server/src/plugins/<key>.ts`，导出 `PluginManifest`：

```ts
import type { PluginManifest } from "../lib/hooks";

export const myPlugin: PluginManifest = {
  key: "my-plugin",
  name: "我的插件",
  version: "1.0.0",
  description: "一句话说明它做什么。",
  author: "你的名字",
  defaultEnabled: false,
  settings: [{ key: "threshold", label: "阈值", type: "number", default: 3 }],
  hooks: {
    filters: {
      "content.renderHtml": (payload, ctx) => {
        const threshold = Number(ctx.config.plugins["my-plugin"]?.threshold ?? 3);
        if (payload.headings.length < threshold) return payload;
        return { ...payload, html: `<div class="notice">本文分 ${payload.headings.length} 节</div>${payload.html}` };
      },
    },
  },
};
```

2. 在 `apps/server/src/plugins/index.ts` 的数组里加一项（**必须加**，否则会被 tree-shaking 掉）。
3. 后台「插件」页启用并配置。

可用钩子见 `lib/hooks.ts` 的 `FilterPayloads` 与 `CallPayloads`。规则：

- `filter` 必须返回**新的** payload 对象，不要原地改；
- `call` 用于副作用，返回值被忽略；
- 插件抛错会被总线捕获并打日志，不会中断页面渲染 —— 但这不意味着可以不做防御。

### 6.2 新增主题

1. 新建 `apps/server/src/theme/<id>/index.tsx`，导出 `Theme`：

```ts
import type { Theme } from "../types";

export const myTheme: Theme = {
  manifest: {
    id: "my-theme",
    name: "我的主题",
    version: "1.0.0",
    author: "你的名字",
    description: "一句话介绍。",
    supports: { darkMode: true, toc: true, sidebar: false, comments: true, moments: true, projects: true },
    settings: [{ key: "accentColor", label: "强调色", type: "color", default: "#b4552d" }],
    styles: `.site { max-width: 72ch; margin: 0 auto; }`,
  },
  render: {
    layout: (ctx, meta, children) => /* ... */,
    home: (ctx, view) => /* ... */,
    archive: (ctx, view) => /* ... */,
    term: (ctx, view) => /* ... */,
    post: (ctx, view) => /* ... */,
    page: (ctx, view) => /* ... */,
    moments: (ctx, view) => /* ... */,
    projects: (ctx, view) => /* ... */,
    search: (ctx, view) => /* ... */,
    error: (ctx, view) => /* ... */,
  },
};
```

2. 在 `apps/server/src/theme/registry.ts` 的 `THEMES` 数组里加一行。
3. 后台「外观」页切换。

八条硬约束（违反会出问题，不是风格建议）：

- renderer 必须**同步**，不返回 Promise；
- 不访问 `db` / `env` / 网络，只用传进来的 view model；
- 输出动态文本一律 JSX 插值，靠自动转义；
- `<style>` / `<script>` 必须用 `dangerouslySetInnerHTML` 或 `raw()` 插入，否则 `>`、`&` 会被转义导致失效；
- 正文用 `<div dangerouslySetInnerHTML={{ __html: view.content.html }} />`，这个 html 已在服务端渲染并过滤；
- 表单用原生 `<form method="post">`，无 JS 也能提交；
- 主题标题不要自己再拼站点名，layout 已经做了去重；
- `manifest.scripts` 里自带 `<script>` 包裹，layout 直接输出，不要再包一层。

### 6.3 新增内容类型

1. `apps/server/src/shared/content-types.ts` 加一条定义（`key` / `label` / `route` / `supports`）；
2. `apps/server/src/site/router.ts` 为它加一个路由前缀（如果它需要独立 URL）；
3. 主题按 `supports` 决定用哪个渲染分支（`post` 渲染器覆盖所有类型，差异靠 `supports` 与内容字段）。

**不需要改表结构**：`contents.type` 是文本列，新类型的字段差异用 `supports` 与自定义字段表达。

### 6.4 新增自定义字段

不需要改代码。后台「内容模型」页 → 新建字段 → 指定 `key`、类型、适用的内容类型。内容编辑页会自动出现这个字段。

字段值落在 `field_values` 表的哪一列由类型决定（见 `shared/content-types.ts` 的 `FIELD_TYPES`）。

### 6.5 新增 API 分组

1. 新建 `apps/server/src/api/<domain>.ts`，导出 `create<Domain>Routes(): OpenAPIHono<AppBindings>`；
2. 在 `apps/server/src/api/index.ts` 里 `app.route("/<domain>", create<Domain>Routes())` 并补一个 tag。

写法照 `api/contents.ts`：`createRoute` 声明 + `app.openapi(route, handler)`，成功走 `ok()` / `created()`，失败 `throw AppError`。**不要用裸 `app.get`**，否则 `/api/doc` 会与实际接口脱节。

### 6.6 新增设置项

`apps/server/src/shared/settings-schema.ts` 加一行 `SETTING_FIELDS`，后台表单自动出现，服务端默认值自动生效。**不需要改表单代码，也不需要迁移**。

键名规则：字段定义里的 `key` 是短名（如 `siteTitle`），存库时前缀成 `site.siteTitle`。

## 7. 排错手册

| 现象 | 排查顺序 |
| --- | --- |
| 访问 `/` 返回后台的 index.html | 检查 `wrangler.jsonc` 的 `assets.run_worker_first` 是否为 `true` |
| 静态资源 404 | 检查 `site/router.ts` 的 `fallbackToAssetsOr404` 是否还在 |
| 改了主题文件但页面没变 | 页面缓存（`site.pageCacheEnabled`）→ 重启 dev → 确认 `theme.active` 指向你改的主题 |
| 改了设置但页面没变 | 同上；另外确认写入走的是 `PATCH /api/settings/site`（会 bump 缓存版本） |
| `/api/*` 返回 HTML | 当日志里出现主题渲染的 404，说明 `app.ts` 里 `/api/*` 的兜底拦截被删了 |
| 查询报 `no such column` | 改过 `schema.ts` 但没跑 `db:migrate` |
| 查询报 `Invalid binding type` | 把 `Date` 塞进了 `sql\`\`` 模板。D1 只接受 string / number / null / ArrayBuffer，先 `.getTime()` |
| 中文搜不到 | 确认写入与查询两侧都走了 `lib/search.ts` 的 `segmentText` |
| 500 且日志无内容 | `wrangler dev` 的 console 输出在启动它的终端里；看 `[requestId] unhandled error` |
| 后台登录后立刻被踢 | 会话解析有 30 秒 KV 缓存；改过权限时先 `env.KV.delete("sess:<tokenHash>")` 或重新登录 |
| `wrangler dev` 起不来，提示找不到 workerd | pnpm 没执行 `workerd` 的安装脚本；确认 `pnpm-workspace.yaml` 的 `onlyBuiltDependencies` 含 `workerd`、`esbuild` |
| 8787 端口被占 | `Get-NetTCPConnection -LocalPort 8787` 找 PID，`Stop-Process -Id <pid>` |

## 8. 部署

### 8.1 准备资源

```bash
npx wrangler d1 create taiping-blog          # 记下返回的 database_id
npx wrangler r2 bucket create taiping-media
npx wrangler kv namespace create KV          # 记下返回的 id
```

把三个 id 回填到 `wrangler.jsonc` 的 `d1_databases[0].database_id`、`r2_buckets[0].bucket_name`、`kv_namespaces[0].id`。

### 8.2 配置

| 名称 | 类型 | 示例 |
| --- | --- | --- |
| `PUBLIC_BASE_URL` | var | `https://blog.example.com` |
| `ENVIRONMENT` | var | `production` |
| `SETUP_TOKEN` | secret（建议） | 一个随机串，`wrangler secret put SETUP_TOKEN` |

`SETUP_TOKEN` 建议设：初始化接口在用户表为空时对外开放，虽然只在部署窗口期有效，但加一道令牌更稳。

### 8.3 上线

```bash
pnpm db:migrate:remote      # 先建表
pnpm deploy                 # 构建 + 部署
curl -X POST https://blog.example.com/api/auth/setup \
  -H 'Content-Type: application/json' \
  -H 'X-Setup-Token: <你的 SETUP_TOKEN>' \
  -d '{"email":"...","username":"...","displayName":"...","password":"...","setupToken":"..."}'
```

### 8.4 上线后自检

| 检查项 | 期望 |
| --- | --- |
| `GET /api/health` | `{"ok":true,...}` |
| `GET /` | 200，HTML 里有站点标题 |
| `GET /rss.xml` | 200，`application/rss+xml` |
| `GET /sitemap.xml` | 200，含已发布内容 |
| `GET /robots.txt` | 200，含 `Sitemap:` |
| `GET /admin` | 200，后台登录页 |
| `GET /api/doc` | 200，`openapi` 字段为 `3.1.0` |
| 登录后发布一篇 | 前台立即可见（无需清缓存） |

## 9. 性能与成本参考

| 项 | 实测值 |
| --- | --- |
| Worker 包体 | 1.45 MB（gzip 269 KB） |
| 首页 TTFB（本地） | 30–60 ms（含缓存未命中） |
| 缓存命中 | 1–5 ms |
| 集成测试全量 | 约 6 秒 |
| 单元测试全量 | 约 1 秒 |
| 口令哈希 | 100k 次 PBKDF2，约 40 ms |

D1 免费额度（每日 500 万行读、10 万行写）对个人博客远远够用。主要成本来自 R2 存储与出网流量，两者在免费额度内也基本够。
