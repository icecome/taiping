# ADR 0006：权限分 `.own` 与 `.any` 两档

- 状态：已采纳
- 日期：2026-10-26
- 相关：[docs/02-CMS架构设计方案.md](../02-CMS架构设计方案.md) 的 5 节

## 背景

「作者只能改自己的文章，编辑能改所有人的文章」是 CMS 最常见的权限需求。三种实现方式：

| 方式 | 做法 | 问题 |
| --- | --- | --- |
| 判角色 | `if (user.role === "admin" \|\| content.authorId === user.id)` | 新增角色要全仓库搜索替换；判定分散在各个 handler 里 |
| 只判权限 | 有 `content.update` 就放行 | 无法表达「只能改自己的」 |
| 权限 + 对象 | 权限键分 `.own` / `.any`，判定时传入对象作者 | 需要把「操作对象」传进判定函数 |

## 决策

**第三种。** 具体规则：

1. 权限键命名 `资源.动作[.范围]`，范围只有两个值：`.own`（仅本人创建的对象）与 `.any`（任意对象）。
2. 判定入口收敛到 `lib/rbac.ts` 的四个函数，业务代码里不允许出现角色判断。
3. `assertContentAccess(auth, action, content)` 根据 `content.authorId === auth.user.id` 自动选择档位。
4. 持有 `.any` 的人处理自己的对象也放行（先试 `.own`，失败再试 `.any`），避免角色配置里漏配 `.own` 造成行为不一致。
5. `owner` 短路放行，不查权限集合 —— 否则新增权限时忘记给 owner 配上，站点所有者会把自己锁在门外。

## 理由

- 权限目录是一份可 diff、可审阅的常量（`shared/permissions.ts`），角色只是它的子集。
- 「改谁的东西」这个信息只在判定点用一次，不需要在每个 handler 里重复写。
- 判定失败时抛出的错误里带上具体权限键（如 `缺少权限：content.update.own`），排查时能直接定位到角色配置。

## 后果

- 所有涉及对象的写操作都必须先把对象查出来（多一次查询），不能「直接按 id 更新」。这是必要的成本：不知道作者就无法判定。
- 新增资源时，如果它有「归属」概念（作者、上传者、创建者），要同时提供 `.own` / `.any` 两个键；没有归属的资源只用一个键。
- 用户管理侧另有一条保护：`assertCanManageUser` 限制非 owner 不能修改 owner 账号，避免管理员通过改别人密码提权。

## 验证

`apps/server/src/lib/rbac.test.ts` 覆盖了作者改自己（放行）、作者改他人（拒绝）、只有 `.any` 的人改自己（放行）、未登录先抛 401 而非 403 等分支。
