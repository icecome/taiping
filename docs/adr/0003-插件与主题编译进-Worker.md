# ADR 0003：插件与主题编译进 Worker

- 状态：已采纳
- 日期：2026-10-26
- 相关：[docs/02-CMS架构设计方案.md](../02-CMS架构设计方案.md) 的 7 节

## 背景

「可扩展」在 CMS 里通常指两件事：第三方可以上传插件包、第三方可以上传主题包。Typecho、Halo 都支持运行时可执行扩展。

但在 Cloudflare Workers 上：

| 方案 | 做法 | 问题 |
| --- | --- | --- |
| 运行时可执行 | 从 R2 拉 JS 后 eval / 动态 import | 沙箱不可靠（拿得到 `env` 就能读全部绑定）、冷启动成本、版本回滚困难 |
| 自带解释器 | 自己定义一套模板/插件 DSL 再解释执行 | 等于自己写一个语言，长期维护成本高 |
| 编译期注册 | 扩展是源码模块，随 Worker 一起部署 | 换扩展要重新部署 |

## 决策

**编译期注册。**

- 插件 = 一个导出 `PluginManifest` 的模块 + 数据库里的启停开关与配置值。新增插件 = 新建文件 + 在 `plugins/index.ts` 注册一行。
- 主题 = 一个导出 `Theme` 的模块 + `theme/registry.ts` 里的一行。
- 钩子沿用 Typecho 的两分法：`filter` 改值（管道）、`call` 副作用。
- 单个插件抛错不影响其它插件与页面渲染：总线捕获异常、打日志、继续。
- 动态扩展的出口留给了**数据面**：`api_tokens`（外部脚本调 API）、webhook（评论通知等）。

## 理由

- 扩展代码与核心代码共享同一套类型，编译期就能发现接口不匹配。
- 部署单元只有一个，回滚 = 回滚一次部署，没有「插件版本与核心版本不匹配」这种状态。
- 冷启动不受插件数量影响（都在同一个包里）。
- 代价是「装插件要重新部署」。对一个自建博客，这个代价远小于维护一个沙箱运行时。

## 后果

- 插件清单在 `apps/server/src/plugins/index.ts` 被显式 import 一次，否则会被 tree-shaking 掉。
- 主题契约（`theme/types.ts`）变更属于破坏性变更，要同时改所有主题并更新本 ADR。
- 不要为了「以后支持运行时插件」而在总线里预留动态加载分支——那会成为无人维护的死代码。
