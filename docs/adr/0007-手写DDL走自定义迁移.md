# ADR 0007：手写 DDL 必须走 drizzle-kit 的自定义迁移

- 状态：已采纳
- 日期：2026-10-26
- 相关：[AGENTS.md](../../AGENTS.md) 的 R7

## 背景

两件事实同时成立：

1. 迁移文件的执行者是 `wrangler d1 migrations apply`，它按目录里的文件名排序执行 `*.sql`，并在 `d1_migrations` 表里记录已执行的文件名。
2. 迁移文件的生成者是 `drizzle-kit generate`，它依据 `migrations/meta/_journal.json` 与快照文件做 diff。

如果直接往目录里丢一个手写的 `0002_xxx.sql`，wrangler 会执行它，但 drizzle 的 journal 不知道它存在。下次 `generate` 时 drizzle 基于上次的快照做 diff，会生成一个同样序号的文件，把刚写的那份覆盖掉，或者产出重复建表的语句。

这不是假想问题：参考项目 LuyBlog 的 `drizzle/meta` 只登记到 0003，而目录里有 0014 个迁移文件；flare-stack-blog 的 journal 停在第 19 条而目录里有 0022。

## 决策

**任何无法由 drizzle schema DSL 表达的 DDL，都用 `drizzle-kit generate --custom` 占位再填内容。**

```
pnpm db:generate --custom --name=create_search_fts
# 生成 apps/server/migrations/0001_create_search_fts.sql（空文件）+ 更新 journal
# 然后把 DDL 写进这个文件
```

当前的实例是 FTS5 虚表 —— `CREATE VIRTUAL TABLE` 无法用 `drizzleTable` 表达，所以它单独占一个迁移位（`0001_create_search_fts.sql`），并且已登记进 journal，后续 `generate` 会从 0002 继续。

## 理由

- 只有一套账本：目录里的每个文件都在 journal 里有对应条目，序号连续、无覆盖风险。
- `wrangler d1 migrations apply` 与 `drizzle-kit generate` 对同一份目录达成一致，不需要人工比对。
- 代价很小：多执行一条命令。

## 后果

- 评审迁移时先看 `meta/_journal.json` 的条目数与目录文件数是否一致，不一致就是有人绕过流程了。
- 手工改已执行过的迁移文件不会生效（wrangler 按文件名记录），要改就得新增一条迁移。
- DDL 不支持事务回滚（SQLite 的 DDL 是事务性的，但迁移是不可逆的），因此写之前先在本地 `pnpm db:migrate` 验证一遍。
