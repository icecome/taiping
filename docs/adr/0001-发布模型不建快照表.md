# ADR 0001：不建公开内容快照表

- 状态：已采纳
- 日期：2026-10-26
- 相关：[docs/02-CMS架构设计方案.md](../02-CMS架构设计方案.md) 的 4.2、10.2

## 背景

参考项目 flare-stack-blog 用一张 `public_snapshot` 表把「后台内容库」与「前台展示库」分开（ADR 0002 / 0008）：发布是一个显式动作，它重建快照，前台只读快照。收益是读路径永远看不到半成品，缓存失效边界清晰。

代价是：多一张表、多一次写入、多一处可能不一致的地方。

## 决策

**不建快照表。** 读一致性由三条规则保证：

1. 内容必须 `status = 'published'`；
2. 必须 `published_at <= now`（或为 NULL）；
3. `deleted_at` 为 NULL。

配合一个全局缓存版本号（见 ADR 0009 的替代方案，即 `lib/cache.ts`）实现全站失效。

## 理由

- 三条规则全部下推成 SQL 条件，与快照表一样保证「读路径看不到草稿」。
- 规则 2 让定时发布**不依赖 cron 准时**：cron 迟到只影响搜索索引刷新，不影响可见性。快照方案反而要担心「快照没重建」这种独立性失败。
- 少一张表就少一处「写完内容忘了同步快照」的 bug 面。这是一个日更一篇的博客，一致性风险比性能收益更值得优化。

## 后果

- 前台每个查询都要带这三个条件。它们被收敛到 `site/data.ts` 的 `publicCondition()`，只有一处实现。
- 无法做「同一内容的多套公开呈现」（参考项目的 ADR 0012 也认为不需要）。
- 旧缓存条目要等 TTL 过期才回收，不支持按 URL 精确失效。个人博客量级可以接受。
