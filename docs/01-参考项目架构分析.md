# 参考项目架构分析

> 分析对象：`docs/flare-stack-blog`（v3.6.1）、`docs/LuyBlog`（nekro-edge-template 0.1.0）
> 目的：为「太平 CMS」重写提供架构依据，明确哪些做法可以直接沿用、哪些在 Cloudflare Workers 上不成立。
> 边界：本文只做架构分析与取舍记录，不含对原项目代码的复制承诺。两份逐文件的深挖笔记见 [`docs/_research/`](./_research/)。

## 1. 为什么先分析而不是先写代码

上一版失败的直接原因是「从零开始设计」，更深一层是**在没有读懂成熟实现的情况下先做技术决策**：内容模型、权限模型、主题机制三件事都是自己发明的，三处叠在一起之后任何一处想改都要动另外两处，最终无法收敛。

所以这次把顺序倒过来：

1. 先把两个参考项目读到能复述它们的表结构、请求调用链与扩展点；
2. 写清楚每个设计在什么运行时前提下成立；
3. 只在「成熟做法」与「当前运行时的真实约束」之间做取舍，不发明第三套。

两个参考项目的定位刚好互补：

| 维度 | flare-stack-blog | LuyBlog |
| --- | --- | --- |
| 形态 | 单仓库全栈应用，前台与后台同一套 React 路由 | 单 Worker 托管 SPA 静态资源 + JSON API |
| 成熟度 | 高：29 篇 ADR、23 条迁移、完整测试分层 | 中：功能齐全，工程规范薄弱 |
| 参考价值 | 架构决策的**结论与理由** | 部署形态与目录划分的**最小可行样板** |
| 主要问题 | 复杂度高，依赖 `bun` 与 2026 beta 的 `cf` CLI，本地复现成本高 | 鉴权、缓存、查询、扩展点四处存在明确缺陷 |

一句话概括：**架构结论取 flare-stack-blog，可部署的骨架取 LuyBlog。**

## 2. flare-stack-blog 架构分析

### 2.1 技术栈与构建链

| 领域 | 选型 | 说明 |
| --- | --- | --- |
| 运行时 | Cloudflare Workers | 单入口 `src/server.ts`，同时暴露 fetch / queue / scheduled 三个触发面 |
| 全栈框架 | TanStack Start 1.169 + React 19 | 文件路由 + SSR，同一份路由定义产出服务端与客户端 |
| 数据 | D1 + Drizzle ORM 0.45 | 19 张业务表 + 1 张 FTS5 虚表 |
| 认证 | better-auth 1.7.6 | session / 邮箱验证 / 找回密码 / API Key 插件 |
| API | oRPC 1.15 + OpenAPI | 由 TypeScript 契约生成 `contract.generated.json`，再产出 OpenAPI |
| 编辑器 | Tiptap 3.20 + `@tiptap/markdown` | 结构化文档，正文不落原始 HTML |
| 样式 | Tailwind CSS 4 | 与后台共用设计令牌 |
| i18n | paraglide-js + inlang | 编译期生成类型安全的文案函数 |
| 包管理与构建 | bun + `cf` CLI（2026 beta） | `cf` 取代 wrangler，仓库打了补丁 |

构建产物落在 `.cloudflare/output/v0/workers/default/bundle`，部署走 `cf d1 migrations apply` + `cf deploy --prebuilt`。

**可复用**：Worker 单入口 + 三个触发面的组织方式；构建期生成契约再产出 OpenAPI 的链路。

**不可照搬**：`bun` 与 `cf` beta CLI。前者要求团队换包管理器，后者是预发布工具且有本地补丁（`patches/cf@1.0.0-beta.5.patch`），把它作为唯一部署路径等于把项目挂在别人的预发布分支上。

### 2.2 Cloudflare 绑定使用情况

| 绑定 | 用途 | 代码位置 |
| --- | --- | --- |
| D1 | 业务主库 + FTS5 全文索引 | `src/lib/db/`、`migrations/` |
| R2 | 媒体原件 | `features/media/` |
| KV | 公开内容快照缓存、站点配置缓存 | `features/cache/server/` |
| Queue | 派生的异步任务（邮件、索引、通知） | `src/lib/queue/` |
| Durable Object ×2 | `PostPublisher`（发布串行化）、`RateLimiter`（强一致计数） | `src/lib/do/` |
| Workers Cache | 页面缓存，配合 Cache-Tag 失效 | `features/cache/` |
| Images | 图片变体（声明了但基本未用） | `cloudflare.config.ts` |

**可复用**：用 Durable Object 解决「同一条内容并发发布」的串行化问题；用 Queue 承接派生任务而不阻塞请求。

**不可照搬**：在个人博客量级上引入两个 DO 与一套 Queue，运维与调试成本远高于收益。定时发布这类需求用 cron + 读时判断即可（见 5.3）。

### 2.3 数据模型

19 张表可归为五组：

| 组 | 表 | 关键设计 |
| --- | --- | --- |
| 认证 | `user` / `session` / `account` / `verification` / `apikey` | better-auth 生成，`session` 存 token 哈希与过期时间 |
| 内容 | `post` / `post_revision` / `post_term` / `term` | 内容与分类标签多对多；修订表存全量快照 |
| 互动 | `comment` / `comment_report` / `muted_user` | 评论正文为纯文本（ADR 0011） |
| 媒体 | `media` | R2 对象键 + 元信息，封面为可空引用（ADR 0020） |
| 系统 | `config` / `friend_link` / `webhook` / `search_index` | 配置以 JSON 存单表（ADR 0025） |

命名与约定统一在 `src/lib/db/schema/helper.ts`：文本主键、时间戳统一列型、`created_at` / `updated_at` 由应用层写入。

**可复用**：
- **分类不是标签**（ADR 0022）。分类负责归档结构，标签负责横向关联，两者不复用同一张表。
- 分类以 `parent_id` 自引用成树，但**不**做级联隐藏——避免"父分类隐藏导致子分类内容消失"这类隐性行为。
- 修订表存全量快照而不是 diff 链。空间换实现复杂度，在博客量级上是正确的方向。

**不可照搬**：把配置整体塞进 JSON 单表。它省迁移，但代价是**所有配置项都无法用 SQL 约束**，写坏的 JSON 只能靠应用层校验兜住。本项目改为 `settings(key, value_json)` 的键值形式，键由代码里的字段定义约束。

### 2.4 认证与权限

- better-auth 的 session 有三种取法：cookie、`Authorization: Bearer`、服务端直读；`get-request-session.ts` 统一封装。
- 服务端守卫分两层：`adminProcedure`（oRPC 中间件）与路由级 `beforeLoad`（TanStack Router）。两层都在，是为了同时挡住"直接调 API"和"直接进页面"。
- API Key 通过 `api-key-guard.ts` 校验，支持权限范围。

**可复用的判断**：**单层角色模型足够**。它只有"管理员 / 普通用户"两档加权限范围，没有引入 RBAC 表。对本项目而言这一点需要反过来做——需求的第 2 条明确要求「权限管理体系」，因此要引入角色表与权限目录，但要沿用它的原则：**权限判定集中在中间件与断言函数里，业务代码不写角色判断**。

**必须修正的问题**：不分 `.own` / `.any`。它的权限判定只看"是不是管理员"，于是"作者能否改别人的文章"这个问题没有答案。本项目把权限键拆成 `content.update.own` / `content.update.any` 两档，判定时必须同时拿到对象作者。

### 2.5 API 层

`src/lib/orpc/` 的职责划分：

| 文件 | 职责 |
| --- | --- |
| `contract.ts` | 定义 procedure 的输入输出 zod schema |
| `contract.generated.json` | 构建期由脚本产出，供 OpenAPI 与客户端共用 |
| `procedure.ts` | procedural 公共件：`publicProcedure` / `authedProcedure` / `adminProcedure` |
| `context.ts` | 每请求上下文（db、session、env） |
| `router.ts` | 把各 feature 的 router 拼成总路由 |
| `error-handler.ts` | 统一错误映射 |
| `server-client.ts` | 服务端直调（SSR 阶段跳过 HTTP） |

一条发布请求的完整路径：浏览器 → TanStack Router loader → oRPC client → `/api/$` → contract 校验 → procedure → service → Drizzle → D1 → service 组装 → procedure 返回 → `unwrap-result.ts` 判断成败 → React Query 缓存更新 → 组件重渲染。

**可复用**：「契约先行 + 单一校验点 + 服务端直调」这三件事。前端不手写类型，接口变更在编译期暴露。

**不可照搬**：oRPC 需要额外的代码生成步骤（`bun run orpc:contract`）。本项目改用 `@hono/zod-openapi`：路由定义里直接写 zod，一次定义同时得到入参校验、类型推导与 `/api/doc`，没有生成物也就没有生成物过期的问题。

### 2.6 内容模型与「公开快照」

这是它最有价值的一块。核心结论出自 ADR 0002 / 0008 / 0012 / 0013：

- **写入模型与读取模型分离**。后台写的是内容库；前台读的是一张"公开快照"投影。
- 发布（publish）是一个**显式动作**，它重建快照并让快照成为唯一的前台数据源（ADR 0008：publish 取代 public snapshot）。
- 评论只有在内容存在公开快照时才允许提交（ADR 0013），避免"评论挂在不存在的页面上"。
- 前台只有一套呈现（ADR 0012），不做多套模板并行。

**这套设计的真实收益**：缓存失效边界清晰——读路径永远只看快照，写路径怎么改都不会让读路径返回半成品。

**它没说的代价**：多一张表、多一次写入、多一处不一致可能。对一个日更一篇的博客，这个代价换来的收益有限。

**本项目的取舍**：保留「发布是显式动作」与「读路径只认已发布状态」，但**不建快照表**。理由见 5.3：本项目用「发布状态 + 读时时间判断 + 全局缓存版本号」达成了同样的读一致性，少一张表。

### 2.7 路由与前端分层

47 个文件路由，按 TanStack Start 的语义分层：

| 段 | 作用 |
| --- | --- |
| `__root.tsx` | 全局布局与错误边界 |
| `_public/` | 访客布局（不带认证） |
| `_public/_auth/` | 登录 / 注册 / 找回密码 |
| `_public/_user/` | 登录后个人中心 |
| `_public/post/$slug` | 文章详情 |
| `admin/` | 后台布局，`beforeLoad` 做鉴权 |
| `api.$.ts` / `api.auth.$.ts` | API 与认证的 catch-all 转发 |
| `rss.xml` / `atom.xml` / `sitemap.xml` / `robots.txt` / `feed.json` / `site.webmanifest` / `stats.js` | 资源路由，直接返回非 HTML |

feature 目录的固定结构（以 `posts` 为例）：

| 目录 | 职责 |
| --- | --- |
| `components/` | 纯展示组件 |
| `data/` | 常量、选项、静态配置 |
| `queries/` | React Query 的 query / mutation |
| `server/` | oRPC procedure（服务端入口） |
| `services/` | 业务逻辑，可被 procedure 与 loader 共同调用 |
| `schema/` | zod 校验 |
| `utils/` | 纯函数 |

**可复用**：这个分层最直接的价值是**"新增功能该往哪放"有唯一答案**。本项目把 `components / queries / server / service / data` 这五层搬到 React 后台，服务端则按 `api / lib / db` 三层划分。

### 2.8 编辑器与渲染

| 组件 | 用途 | 位置 |
| --- | --- | --- |
| Tiptap | 结构化编辑器（表格、任务列表、数学、图片、视频） | `features/posts/editor/` |
| `@tiptap/markdown` | 与 Markdown 双向转换，含 8 处自定义序列化 | 同上 |
| Shiki | 代码高亮，59 种语言按需加载 | `src/lib/shiki.ts` |
| KaTeX | 数学公式，条件加载 | 编辑器扩展 |
| Mermaid | 图表，**只能在访客浏览器渲染**（ADR 0027） | 前端 |
| `@tiptap/static-renderer` | SSR 阶段把文档 JSON 直接渲染成 HTML | 前台渲染 |

**关键结论**：正文以**结构化 JSON** 为准，HTML 是派生物。这样前台不需要消毒（不存在用户可控的原始 HTML），也避免了「Markdown 渲染 + DOMPurify」这条在 Workers 上要靠 `jsdom` 才能跑的路。

**本项目的取舍**：改用 Markdown 为唯一真源，但**关闭原生 HTML 透传**，配合「评论纯文本 + 模板转义」达成同等安全性，同时不引入编辑器体积。理由见 5.4。

### 2.9 搜索、SEO 与订阅

- 搜索：D1 FTS5 虚表 + `Intl.Segmenter` 预分词（ADR 0023）。分词在写入与查询两侧都做，口径一致。
- SEO：`src/lib/seo.ts` 提供三个出口（页面 meta、结构化数据、订阅源）。
- 订阅：`rss.xml` / `atom.xml` / `feed.json` / `sitemap.xml` / `robots.txt` / `site.webmanifest` 各自独立成路由。

**可复用**：FTS5 + Segmenter 的组合是 Workers 上做中文搜索的正解，本项目直接沿用（见 `lib/search.ts`）。

### 2.10 工程化

| 项 | 做法 | 评价 |
| --- | --- | --- |
| Lint / Format | oxlint + oxfmt | 快，但生态较新 |
| 测试 | 两套 vitest 配置：`vitest.config.ts`（集成，跑在 workerd）、`vitest.node.config.ts`（纯函数） | **直接沿用** |
| i18n | paraglide + 文案校验脚本（校验缺失与未使用） | 有用，但本项目暂不需要 |
| 迁移 | 23 条，drizzle-kit 生成 + 手写补位 | **有漂移问题**：journal 只到 idx 19，目录里有 0022 |
| 发布 | release-it + conventional changelog | 单人项目可省 |

**直接沿用的**：双 vitest 配置的分工——纯函数在 Node 跑得快，需要绑定的走 workerd。

**明确规避的**：迁移漂移。本项目的规则是：结构变更一律 `drizzle-kit generate`；FTS 这类无法用 schema DSL 表达的 DDL 用 `drizzle-kit generate --custom` 占位，让它也登记进 journal，从而不产生第二条账本。

## 3. LuyBlog 架构分析

### 3.1 形态与目录

它是「一个 Worker 干三件事」的最小样板：

| 部分 | 目录 | 说明 |
| --- | --- | --- |
| Worker 入口 | `src/index.ts` | Hono 应用，挂载 API、鉴权、静态资源、SSR 兜底 |
| 数据层 | `src/db/schema.ts` | 单文件 Drizzle schema |
| API | `src/routes/*.ts` | 按领域分文件，`@hono/zod-openapi` 出文档 |
| 共享校验 | `common/validators/` | 前后端共用 zod schema |
| 前端 | `frontend/` | React 18 + Vite + MUI，构建产物被 Worker 当静态资源托管 |
| 迁移 | `drizzle/` | 15 条，0000–0014 |
| HTML 模板 | `scripts/generateHtml.ts` | 构建期生成页面骨架的 meta |

`wrangler.jsonc` 里 `main: src/index.ts` + `assets.directory: ./dist/client`，即「Worker 与 SPA 同源托管」。

### 3.2 部署拓扑与一个被忽略的坑

它把 `assets` 声明成目录绑定，但**没有设 `run_worker_first`，也没有设 `not_found_handling`**。平台默认行为是「命中同名静态文件就直接返回」，于是 `/` 会命中 `dist/client/index.html`，`src/index.ts` 里那一段 SSR 分支实际上只对「没有同名文件的路径」生效。

代码是按「所有非 `/assets` 路径都走 SSR」写的（`src/index.ts:111-120`），意图与平台行为不一致，结果是首页的 SEO meta 来自构建期静态模板而不是运行时数据。

**本项目的处理**：`run_worker_first: true`，由 Worker 显式决定什么交给 ASSETS、什么自己渲染。代价是所有请求多一个 Worker 调用的开销，换来行为完全可预期。

### 3.3 数据模型

15 条迁移里能读出清晰的演进：

| 迁移 | 内容 | 说明 |
| --- | --- | --- |
| 0000–0002 | 建表、建基础模型 | 一次到位 |
| 0003 | `drop_features` | 砍掉早期预留的功能表 |
| 0004 | 内容结构调整 | 与 Halo 导入配合 |
| 0005–0014 | 音乐、友链、站点设置、浏览量、导航 | 功能逐个追加，其中 0006 / 0007 / 0014 又砍掉了音乐与瞬间图片 |

**读出来的结论**：迁移目录本身就是一部失败尝试的记录——**预留字段和预留表最后大多被删掉**。本项目的对策是：内容类型只留四个（文章、页面、动态、项目），且它们的差异用「能力声明」表达，不再为想象中的需求建表。

表结构上，`posts` 的 `tags` / `category` 是**文本列**而不是关联表。这是最省事的写法，代价是无法按分类做分页查询、无法统计计数、改名要全表扫描。

### 3.4 鉴权模型（本次分析里最需要修正的部分）

| 项 | 现状 | 后果 |
| --- | --- | --- |
| session token | `createId()` 生成（cuid2，非 CSPRNG），**明文**存 `user_sessions` | 泄库即等于账号被接管 |
| 有效期 | 固定 30 天，无轮换、无单条撤销 | 令牌泄露后只能改库 |
| 存储位置 | 前端 localStorage | 任意 XSS 直接读走 |
| 角色模型 | `user` / `admin` 二值 | 无法表达「作者只能改自己的」 |
| 写操作 | 不看 `author_id` | 任何管理员可改任何内容，且无法审计到人 |
| `users.api_key` | 生成后明文回传、从未参与鉴权 | 死字段，同时是一个泄露面 |

**本项目的修正**：

1. token 由 32 字节 CSPRNG 生成，库里只存 SHA-256，泄露库也无法伪造会话；
2. 会话可单条吊销、可按用户批量吊销（改密、停用、角色变更都会触发）；
3. 凭证只走 HttpOnly + SameSite=Lax cookie，不落 localStorage；
4. 权限拆 `.own` / `.any`，判定必须带对象作者；
5. 写操作全部落审计日志。

### 3.5 查询与缓存

| 问题 | 位置 | 后果 |
| --- | --- | --- |
| 读接口带写副作用 | `src/routes/post.ts:83-87`，`GET /posts/:slug` 自增 `view_count` | 无法缓存、304 也计数、写放大 |
| 全量拉内存过滤 | `/api/search` 一次拉 5 张表后 `includes` | 内容一多就拖垮 CPU 预算 |
| 前台归档硬编码上限 | 固定 `posts(100)` | 超过 100 篇静默丢内容 |
| 后台列表先拉 100 条再本地 `find` | `adminApi.post(id)` | 第 101 条起查不到 |
| 分类去重逻辑重复两处 | `taxonomy` 两条路径 | 改一处漏一处 |

**本项目的修正**：

- 浏览量改为「读时累加 + 定时落库」，读路径不再写库；
- 搜索走 FTS5，归档与列表全部走 SQL 分页与 `count(*)`；
- 上层接口强制 `pageSize` 上限 100，但**下推**到 SQL；
- 分类计数用一条 `UPDATE ... (SELECT COUNT ...)` 重算，只有一处实现。

### 3.6 内容安全

`MarkdownView` 开着 `rehype-raw` 且不做消毒，与「token 存 localStorage」组合成一条完整链路：后台作者写入恶意 HTML → 访客页面执行 → 读走同源 localStorage 里的令牌 → 接管后台。

**本项目的修正**：Markdown 渲染关闭原生 HTML 透传，评论正文按纯文本存储、模板层转义。详情见 `docs/adr/0002-内容安全的边界.md`。

### 3.7 其他可复用的部分

| 做法 | 价值 |
| --- | --- |
| `common/validators/` 前后端共用 schema | 校验规则只有一份，前端能提前提示 |
| `@hono/zod-openapi` 一次定义出文档 | 没有代码生成步骤，文档不会过期 |
| `scripts/generateHtml.ts` 生成页面骨架 | 构建期确定 meta 结构，运行时只填内容 |
| 后台按模块分页（仪表盘 / 站点 / 导航 / 文章 / 瞬间 / 项目 / 页面 / 友链 / 评论 / 用户） | 模块划分与内容模型一一对应，容易对照 |

## 5. 关键取舍与理由

这一节是本文的结论部分。每条都是「参考项目这么做，本项目不那么做」的显式决策。

### 5.1 前台用服务端 JSX，后台用 React SPA

- 前台需要 SEO 与首屏，但**不需要**客户端路由与 hydration。用 `hono/jsx` 在 Worker 上渲染成纯 HTML，主题是一组 TSX 组件，产物零 JS 框架运行时。
- 后台需要复杂交互（编辑器、拖拽排序、批量操作），用 React + TanStack Query 构建成 SPA，构建产物由同一个 Worker 当静态资源托管。
- 这条边界同时解决了一个现实问题：Worker 包里**不含 React**，冷启动与包体积都可控（实测包体 1.4 MB、gzip 269 KB）。

### 5.2 主题是编译进 Worker 的模块，不是可上传的模板包

- Workers 里做「运行时可执行模板」要么走动态 `import`（受限），要么自己实现解释器。两条路都带来 RCE 面与冷启动成本。
- 主题编译进包以后：换主题要重新部署，但换来完整类型检查、零解析开销、无执行面。
- 主题与数据层严格分离：主题只接收 view model，不接触 `db` / `env`。

### 5.3 不建公开快照表，用「状态 + 读时判断 + 缓存版本号」

- 读一致性由三条规则保证：内容必须 `status = published`；必须有 `published_at` 且不晚于当前时间；未进回收站。
- 定时发布因此**不依赖 cron 准时**：cron 迟到只会影响索引刷新，不影响可见性。
- 缓存失效用一个全局版本号：发布、改设置、切主题都 bump 版本，缓存键前缀随之变化，一次写入即全站失效。
- 代价：旧缓存条目要等 TTL 过期才被回收，无法按 URL 精确失效。个人博客量级可以接受。

### 5.4 Markdown 关闭 HTML 透传，而不是引入消毒库

- Workers 没有 `document`，`DOMPurify` 需要 `jsdom`，这条路本身就重。
- 关掉原生 HTML 之后，正文 HTML 完全由渲染器拼出来，属性值统一转义，服务端不需要消毒库。
- 评论正文按纯文本存、模板层转义；这也与 flare-stack-blog 的 ADR 0011 结论一致。
- 代价：作者不能在正文里直接写 HTML。需要嵌入组件的场景（视频、图表）留作插件钩子的扩展点。

### 5.5 插件编译期注册，不做动态加载

- 插件 = 一个导出 `PluginManifest` 的模块 + 数据库里的启停开关与配置值。
- 钩子语义沿用 Typecho 的两分法：`filter` 改值、`call` 副作用。
- 新增插件 = 新建一个文件 + 注册一行，不改总线、不改调用点。
- 动态加载留白但不实现：需要时用 webhook 这类**数据面**扩展，而不是把第三方代码跑进 Worker。

## 6. 从两个项目里提炼的通用教训

| 教训 | 证据 | 本项目如何落地 |
| --- | --- | --- |
| 先读再写 | 上一版三套自研模型互相纠缠 | 本文档即前置产物 |
| 迁移目录就是设计史 | LuyBlog 15 条迁移里 4 条在砍功能 | 只保留四个内容类型，能力用声明表达 |
| 预留字段最终会被删 | 同上 | 不为想象中的需求建表 |
| 读接口不能有写副作用 | `GET /posts/:slug` 自增浏览量 | 浏览量定时落库 |
| 缓存与鉴权必须一起设计 | localStorage 存 token + 内联 HTML | HttpOnly cookie + CSP + 关闭 HTML 透传 |
| 平台默认行为要显式覆盖 | `assets` 未设 `run_worker_first` | 显式设 `run_worker_first` 并在 Worker 里分派 |
| 两套账本必然漂移 | drizzle journal 与 SQL 目录不一致 | 手写 DDL 也走 `--custom` 登记进 journal |
| 权限要能回答「改谁的东西」 | 只有 `admin` 二值 | `.own` / `.any` 双档 |
| 复杂度要匹配规模 | 两个 DO + Queue + 快照表 | cron + 任务表 |
