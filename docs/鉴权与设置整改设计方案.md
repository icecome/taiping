# 鉴权与站点设置 · 整改设计方案

> 范围：仅设计方案，**本轮不改代码**。  
> 依据：现有实现通读 + 既有审查报告 + Halo/Typecho 对照。  
> 约束：单管理员个人博客、Cloudflare Worker + D1、变更最小化、安全务实。  
> 措辞：采用「建议 / 倾向 / 通常」，避免绝对化断言。

---

## 0. 目标与非目标

| 目标 | 非目标（建议暂缓） |
|------|-------------------|
| 会话与密钥「失败闭合」，避免静默降级 | 多用户 / RBAC / 组织账号 |
| CSRF 与 XSS 防护形成可解释的边界 | WebAuthn / TOTP 2FA（个人博客收益有限） |
| 设置读写对脏数据稳健，密钥不进业务库 | 完整设置版本管理 / 多站点 |
| 配置分层清晰：env=密钥，D1=业务配置 | 把 GitHub Token、会话密钥写入 settings 表 |
| 与内容域新模型兼容（解锁、镜像、图床） | 重写整个 Studio 壳子 |

## 1. 现状评估

### 1.1 鉴权 — 已具备的基础（倾向保留）

| 能力 | 现状 | 证据 |
|------|------|------|
| 单管理员 | `admins` 表，username UNIQUE | `migrations/0002_admins.sql` |
| 口令存储 | PBKDF2-SHA256，10 万次（Workers 上限），带盐与版本前缀 | `lib/crypto.ts:8-29` |
| 会话 | D1 `sessions` + HMAC 签名 Cookie（`id.exp.sig`） | `services/auth.ts:156-181,402-433` |
| 有效期 | 受信 7 天 / 默认 6 小时 | `auth.ts:11-12` |
| 登录防护 | IP 5 次/15 分钟；账号 10 次/60 分钟；成功清失败 | `authAttempts.ts` |
| 恒定时间比较 | 用户名 + 口令均已覆盖 | `auth.ts:219-222`、`crypto.ts:102-121` |
| 首次初始化 | env 播种 或 空库 `register` | `account-bootstrap.md`、`auth.ts:45-141` |
| 口令重置 | 邮件链接，令牌只存哈希，30 分钟，单次消费 | `auth.ts:268-371` |
| CSRF 头 | 非 GET 要求 `X-Requested-With: XMLHttpRequest` | `middleware/auth.ts:35-40` |
| 加密文解锁 | 独立 HMAC 令牌 Cookie，Path 限定 | `auth.ts:435-458` |

**总体倾向**：鉴权主链路（登录、会话、限流、重置）设计完整度高于同体量个人博客常见水平；问题主要在**边界闭合与配置分层**，而非推倒重来。

### 1.2 鉴权 — 建议整改点

| 级别 | 问题 | 说明 | 证据 |
|------|------|------|------|
| **P0** | `SESSION_SECRET` 缺失仅告警 | `fetch` 路径 `warnEnvOnce`，空密钥仍可签发可预测会话，属静默降级 | `index.ts:67-68`、`env.ts:83-96`；审查 M-S5 |
| **P0** | CSRF 仅自定义头 | 站内 XSS 可自行带该头；与评论外链 XSS 历史问题叠加时，管理员会话操作面偏大 | `middleware/auth.ts:35-40`；`reviews/03` |
| **P1** | 无「会话列表 / 单设备吊销」 | 改密会 `DELETE FROM sessions` 全清，无法只踢掉可疑设备；设计文档曾规划设备管理 | `auth.ts:258-265` |
| **P1** | `forgot-password` 未单独限流 | 登录/注册有 attempts，重置申请侧未见独立计数，存在邮件轰炸面 | `admin.ts:196-221` |

| **P2** | 无「强制下线全部」独立入口 | 等价于改密副作用；可显式暴露为「退出所有设备」 | — |

## 2. 与开源实践的对照（只借所需）

| 主题 | Typecho | Halo | 对本项目建议 |
|------|---------|------|--------------|
| 账号模型 | users 多角色 | User + RBAC + API Token | **维持单管理员**，不引入角色表 |
| 会话 | PHP Session / Cookie | 独立 session 体系 | 维持 D1 session + 签名 Cookie；补设备列表即可 |
| 配置 | `options` 表 | SystemSetting Extension | 维持 `settings` KV；加强校验与缓存，不抄 Extension |
| CSRF | 表单 token 插件常见 | Spring Security | 从「双提交 Cookie」或「Origin 校验 + 自定义头」二选一加固 |
| 密钥 | 配置文件 | 环境/安装向导 | **密钥只走 env / wrangler secret**（维持现状） |

## 3. 鉴权整改方案

### 3.1 P0 — 失败闭合与 CSRF 加固（建议优先）

#### 3.1.1 环境失败闭合

**建议**：`fetch` 入口在「需要鉴权或签发会话/解锁令牌」的路径上，对缺失/占位 `SESSION_SECRET` 直接 500 或 503，而不是仅 `warnEnvOnce`。

| 方案 | 做法 | 利 | 弊 |
|------|------|----|----|
| **A. 全局 assertEnv（推荐）** | `fetch` 开头 `assertEnv`，Cron 保持 | 实现最简、无静默 | 本地忘配 secret 时前台 500（可接受，提示明确） |
| B. 按路由 assert | 仅 admin/unlock 路径强校验 | 前台只读可降级 | 分支多，易漏 |

**倾向 A**：个人博客 Worker 启动成本低，失败闭合优先于「少一页可看」。

#### 3.1.2 CSRF

| 方案 | 做法 | 利 | 弊 |
|------|------|----|----|
| **A. Origin/Referer 校验 + 现有自定义头（推荐）** | 非 GET 校验 `Origin`（或退化 `Referer`）与站点同源；保留 `X-Requested-With` | 无状态、与 SPA 契合、改动小 | 反代剥 Origin 时需兼容 |
| B. 双提交 CSRF Token | 登录下发 `tp_csrf` 非 HttpOnly Cookie，请求头回传并比对 | 抗 CSRF 更标准 | 前后端各多一跳；需防 Cookie 注入 |
| C. SameSite=Strict | Cookie 改 Strict | 实现最省 | 跨站入口跳转会丢会话，体验差 |

**倾向 A**，若后续接第三方后台再考虑 B。XSS 仍需靠渲染净化（评论/主题）兜住——CSRF 不能替代 XSS 防护。

### 3.2 P1 — 会话治理与口令策略

1. **会话列表 API**（单管理员设备管理）  
   - `GET /api/admin/auth/sessions` → `{ id, createdAt, expiresAt, trusted, userAgent, current }`  
   - `DELETE /api/admin/auth/sessions/:id` 吊销非当前  
   - `POST /api/admin/auth/sessions/revoke-others`（或复用改密的全清，显式命名）  
   - 表结构可复用 `sessions`，无需新表；建议补 `last_seen_at`（可选，P2）。

2. **口令策略收敛**  
   | 方案 | 做法 | 利 | 弊 |
   |------|------|----|----|
   | **A. 登录与新建统一 ≥8（推荐）** | `LOGIN_PASSWORD_MIN` 升到 8；历史短口令下次登录失败则走重置/改密 | 策略简单 | 未改密前无法登录，需重置邮件或 env 播种文档 |
   | B. 登录保持 4，新建 8，后台弱口令提示 | 兼容历史 | 策略分裂 | 弱口令长期存在 |

3. **forgot-password 限流**  
   - 复用 `auth_attempts` 或轻量计数：同 IP 15 分钟 ≤3 次；响应始终 `{ submitted: true }`。

### 3.3 P2 — 细节与体验

- logout 的 Cookie 属性与 `issueSession` 对齐（动态 `Secure`）。  
- `AUTH_PUBLIC_PATHS` 改为「相对 admin 路由 path 规范化后比较」，去掉重复全路径。  
- 改密 / 全量吊销后，前端统一 `goToLogin`（现已部分如此）。  
- 可选：会话 Cookie `Path` 保持 `/`（解锁与后台同域需要），但后台敏感操作强制较短 TTL 会话（trusted=false 仅 6h）——**维持现状即可**。

### 3.4 鉴权明确建议不做

- 多角色、OAuth 登录、魔法链接登录、2FA  
- 把 `SESSION_SECRET` / GitHub Token 存入 `settings`  
- 无状态 JWT（与可吊销会话目标冲突，且文档已论证过服务端会话更合适）

## 4. 站点设置整改方案

### 4.1 P1 — 稳健性与引用完整性

1. **写入路径**  
   - `PATCH /settings`：`safeParse({ ...current, ...body })`  
   - 失败时返回 `VALIDATION_FAILED` + zod `details`（字段级），**避免未捕获 zod 抛进 INTERNAL**。  
   - 数值沿用 `clampInt`；布尔严格 `z.boolean()`，避免 `'false'` 真值坑。

2. **媒体配置引用**  
   - `activeMediaConfigId` 必须 ∈ `mediaConfigs[].id`，或清空并回落第一项。  
   - 删除配置时若为 active，自动改指或清空。

3. **缓存（轻量）**  
   | 方案 | 做法 | 利 | 弊 |
   |------|------|----|----|
   | **A. 进程内 isolate 缓存 + 版本号（推荐）** | `settings` 表可复用/重建 `cache_versions` 或固定 key；读缓存 30–60s；写时 bump | 改动小、够用 | 多 isolate 短暂不一致 |
   | B. KV 缓存 | 绑定 CACHE 时写 KV | 跨请求一致更好 | 无 KV 时双路径 |
   | C. 不缓存 | 维持每请求读 | 零风险 | 前台 QPS 高时 D1 压力 |

   个人博客流量下 **A 即可**；B 作可选增强。

### 4.2 P2 — 可维护性

1. **废弃键清理**：`saveSettings` 时删除 `settings` 中不在 schema 的 key（或提供「清理无效键」按钮）。  
2. **`createMediaConfig`**：改用 `createId('mc')`，展开顺序改为 `{ ...defaults, ...partial, id }`。  
3. **`settingFields` 与 schema 同源**：用 `keyof SiteSettings` 约束 `name`，漏配能在 typecheck 暴露。  
4. **主题 URL 纵深**：`components.ts` 输出导航/社交 `href` 前走 `safeNavHref`（与评论同一套）。  
5. **分组扩展**：预留 `security` 分组（只放「会话/口令」跳转说明或「强制 https 提示」），**密钥仍不进表**。

### 4.3 设置与环境的边界（建议成文）

| 类别 | 存放 | 示例 |
|------|------|------|
| 密钥 / 凭证 | env（wrangler secret） | `SESSION_SECRET`, `GITHUB_TOKEN`, `RESEND_API_KEY`, `RESEND_WEBHOOK_SECRET` |
| 部署形态 | env | `ADMIN_PATH`, `INBOUND_REPLY_DOMAIN` |
| 可公开业务配置 | D1 `settings` | 标题、导航、评论策略、图床 owner/repo/CDN 模板 |
| 账号资料 | D1 `admins` | username, password_hash, email |

**建议**：GitHub 图床继续「非机密配置进 settings + Token 仅 env」；若未来要多 Token，再评估 D1 加密列或 Secrets，不在本轮展开。

### 4.4 设置明确建议不做

- 把管理员口令或第三方 Token 写入 settings 并经管理 API 明文回读  
- 完整 CMS 级配置版本树  
- 为单管理员引入权限矩阵配置页

## 5. 与内容域的衔接

| 衔接点 | 约定 |
|--------|------|
| 加密文章解锁 | 令牌仍用 `SESSION_SECRET`；若 P0 失败闭合，解锁与会话同时被保护 |
| 镜像 / 图床 | Token 继续 env；settings 只存 repo/路径/CDN |
| 评论白名单/审核 | 仍读 settings；不在鉴权改造中改语义 |
| 后台入口 `ADMIN_PATH` | 保持 env；与 CSRF Origin 校验用请求 Host，不依赖 settings.url |

## 6. 分期与验收建议

### Phase A（P0，建议 0.5–1 天）

- [ ] `fetch` 路径 `assertEnv`（或等价失败闭合）  
- [ ] 非 GET 校验 Origin/Referer + 保留自定义 CSRF 头  
- [ ] 用例：缺 `SESSION_SECRET` 时登录/发帖被拒；伪造 Origin 被拒  

### Phase B（P1，建议 1–2 天）

- [ ] 会话列表与吊销  
- [ ] forgot-password 限流  
- [ ] 口令策略收敛（方案 A 或 B 二选一）  
- [ ] settings 写入 `safeParse` + 字段错误回显  
- [ ] `activeMediaConfigId` 引用校验  
- [ ] settings 读缓存（isolate + 版本）  

### Phase C（P2，按需）

- [ ] logout Secure 对齐、公开路径表整理  
- [ ] 废弃键清理、createMediaConfig 统一 ID  
- [ ] 主题 `safeNavHref` 纵深  
- [ ] settingFields 类型约束  

### 验收清单

- [ ] 无 `SESSION_SECRET`：明确错误，不签发可验证会话  
- [ ] 跨站 Origin 的 PATCH 设置 / 发布文章：403  
- [ ] 正常 Studio 保存设置、登录、发布：不受影响  
- [ ] 脏 settings 行：前台可渲染，后台保存可纠错  
- [ ] 吊销非当前会话后，旧 Cookie 立即 401  
- [ ] 忘记口令连点：有限流且不泄露账号是否存在

## 7. 决策待确认（实施前）

1. **口令策略**：统一 ≥8（推荐）还是登录保持兼容 4？  
2. **CSRF**：Origin 校验 + 自定义头（推荐）还是双提交 Token？  
3. **环境失败闭合**：全局 assert（推荐）还是仅鉴权路由？  
4. **settings 缓存**：isolate 短 TTL（推荐）还是继续每请求读？  

确认后可按 Phase A → B → C 开工；建议每次只合入一个 Phase，便于回滚。
